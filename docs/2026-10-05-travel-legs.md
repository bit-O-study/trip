# 일정 사이 거리·이동정보

## 동작

- 각 일정에서 이전·다음 일정의 거리를 표시한다. 날짜 경계를 넘는 인접 일정도 포함한다. 좌표가 없으면 계산 불가로 표시하며 임의의 좌표를 쓰지 않는다.
- 자동 값은 WGS84 대권 직선거리다. 실제 도로·철도·항공 경로 거리가 아니며, 실제 이동거리를 km 단위로 직접 입력할 수 있다.
- 도보·자전거·자동차·택시·버스·지하철·기차·비행기·배·기타를 고르고 분 단위 소요시간을 저장한다. 자동 경로/교통 API는 호출하지 않는다.
- 이동정보는 방향이 있는 두 일정 ID에 연결된다. 재정렬 후 새로 인접해진 쌍에는 기존 다른 구간의 값을 붙이지 않는다. 장소가 바뀌면 재확인 안내를 표시하고 수동 거리는 무효화한다.
- 기존 구간을 동시에 수정하면 version으로 충돌을 감지한다. 소유자·편집자만 저장하고 조회자는 읽기만 한다. 두 일정은 반드시 같은 여행에 속해야 한다.
- 입력창은 열었을 때만 렌더한다. 열려 있는 동안 카드 드래그를 꺼 터치 스크롤과 충돌하지 않는다.
- 여행 JSON 내보내기는 schemaVersion 2이며 travelLegs를 포함한다.

## 배포 전제

운영 코드 전환 전에 `supabase/migrations/20261005000001_travel_legs.sql`을 **trip 전용 프로젝트 mtocrrzmhucrrkcqxxeo**에 적용해야 한다. 다른 프로젝트의 DB를 사용하지 않는다. 현재 확인된 환경변수에는 trip DB 연결정보가 없다. 공개 Supabase 키로는 DDL을 실행할 수 없다.

1. gitignored `.env.local`에 이 프로젝트의 `SUPABASE_DB_URL`을 설정한다.
2. 저장소 DB 도구로 대상 스키마를 점검하고 마이그레이션을 적용·검증한다 (`supabase/README.md`).
3. 실제 Supabase에서 owner/editor 저장, viewer/비회원 거부와 로그인 후 일정 로딩 시간을 확인한다.
4. 이 브랜치를 main에 병합하고 배포한다. DB 변경 전에 병합하면 이동정보 조회가 실패한다.

## 검증

- lint, TypeScript, 전체 310개 테스트 통과. 실제 SQL을 PGlite에 적용해 읽기/쓰기 권한 거부·여행 간 연결 금지·cascade를 검증했다.
- 실제 컴포넌트/CSS 브라우저 검사: 320/390/768/1280px에서 드래그, 장소 검색 수정, 장소→시간, 체크인/체크아웃, 메모, 이동정보 제출, 가로 넘침 없음. 외부 API와 서버 액션은 대체했다.
- 390px 개발 브라우저 fixture에서 일정 200개 렌더 451ms, 닫힌 이동 입력 폼 0개. 네트워크/로그인/운영 DB 성능을 의미하지 않는다.
- 실제 운영 DB 적용 및 인증된 사용자 데이터의 E2E는 DB 접속정보를 받으면 이어서 검증해야 한다.
