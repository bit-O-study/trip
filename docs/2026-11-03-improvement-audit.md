# 트립앱 전체 개선 점검

2026년 11월 3일 현재 작업 트리 기준이다. 기존 미커밋 변경을 포함해 검토했다. 우선순위는 **조회 지연과 데이터 일관성 → 검색과 지도 사용성 → 운영 검증 → 확장 기능**이다. 아래 반영 내역은 로컬 코드 변경이며 운영 배포는 별도다.

## 이번에 반영한 개선

- 상세 일정과 투표 마감의 경합을 수정했다. 정상 방문은 병렬 조회하고 마감이 있었을 때만 일정을 다시 읽는다. 투표 조회 실패는 안내와 함께 일정 화면으로 복구한다.
- 참여자·공유 설정을 Suspense 경계로 분리했다. 참여자·공유 조회 오류 때문에 일정 전체가 실패하지 않는다. 공유 목록은 소유자 화면에서만 조회한다.
- 이동 정보 조회 실패 시 안내하며 해당 이동 편집은 막아, 실패를 빈 데이터로 오인해 저장하지 않게 했다.
- 장소 검색 공급자 판정은 전체 일정·메모·항공 스냅샷 대신 좌표 필드만 조회한다.
- Google 장소 검색은 8초 timeout, 브라우저 검색은 15초 timeout과 취소를 제공한다. 이전 요청의 늦은 응답은 무시한다.
- 장소 검색 더보기와 공급자·장소 ID 기준 중복 제거를 추가했다. 더보기 실패 시 기존 결과를 유지한다. Google의 페이지 확장은 새로 추가하지 않았다.
- 지도 오류 화면에서 개발자용 설정 지시를 제거하고 목록 이용 안내·네트워크 오류 재시도를 제공한다. 지도 범례가 지도 높이 밖의 영역을 침범하지 않도록 분리했다.
- 동일한 지도 데이터로 마커를 다시 만들지 않는다. 제목·방문 순서 변경 시 지도 확대 범위를 유지하고 실제 좌표 구성이 바뀔 때만 범위를 재설정한다. 언마운트 때 overlay를 정리한다.
- 데스크톱은 왼쪽 일정·오른쪽 고정 지도, 모바일은 지도·일정 세로 배치로 구성했다. 지도 선택 시 reduced-motion 설정을 따른다.
- 날짜별 숙박 표시의 시간대 변환을 숙박당 한 번으로 줄였고, 여행 목록의 상태·검색 문자열·출발 표시를 재사용한다. 투표 후보도 투표별로 한 번 색인한다.
- 일정 추가의 장소·항공·직접 입력 폼을 지연 로드한다. 한 번 연 폼은 화면 안에서 유지해 모드 전환·닫기·취소 후에도 초안을 보존한다. 페이지 새로고침·다른 경로로 이동한 뒤의 초안 복원은 포함하지 않는다.
- 종료 시각과 저장된 이동시간이 있고 위치 정보가 유효한 구간에 한해 다음 일정까지 부족한 시간을 표시한다. 종일·미입력·변경된 위치에는 추측 경고를 만들지 않는다.
- 기존 실패 테스트의 환경·RPC 기대값·국내외 자동 좌표 정책을 정리했다. 마감 직후 일정, 검색 취소·늦은 응답·더보기, 지도 변경 기준, 연박 색인, 이동시간 충돌에 회귀 검사를 추가했다.
- README의 DB 명령과 항공·공유 구현 상태를 갱신했다. 전체 테스트 중 워커 종료 지연이 관찰돼 Vitest 동시 실행 수를 4로 제한했다.

검증 결과: lint·typecheck·생산 빌드 통과, 전체 44개 테스트 파일의 **409건 통과**. `verify-mobile-ui.mjs`와 새 `verify-board-ui.mjs` 모두 320/390/768/1280px 통과. 전자는 실제 카드·폼과 서버 액션 모형, 후자는 실제 보드·폼과 지도/서버 액션 모형을 사용한다. 200개 카드 로컬 브라우저 fixture는 이번 실행에서 306ms였으며 운영 속도 또는 개선율을 뜻하지 않는다.

운영 로그인 E2E, 실제 지도 공급자 연결, DB 실행계획·운영 응답시간 측정은 남아 있다. 운영 DB 변경·배포·런타임 업그레이드는 실행하지 않았다. 아래 백로그의 서버 집계·페이지네이션·오프라인·계정 탈퇴·확장 기능은 이번 반영 범위 밖이다.

## 내부 DB 검토 결과

사용자는 성능상 필요하면 서버 내부 DB에 트립 전용 스키마를 만드는 방식을 허용했다. 2026년 11월 3일 관리 서버에서 읽기 전용으로 확인한 결과, 현재 운영 설정은 외부 Supabase를 가리키고 있으며 내부 PostgreSQL에는 기존 이전 후보 `bito_trip_cutover`가 있다. 후보 DB의 `trip` 스키마에는 13개 테이블, `auth`에는 27개 테이블이 존재한다. 따라서 새 스키마를 중복 생성하거나 기존 후보를 덮어쓰지 않았다.

관리 서버에서 외부 `/auth/v1/health` 3회 호출은 1200/82/28ms, 내부 후보 DB에 psql로 새 접속 후 `select 1` 실행은 56/52/50ms였다. 외부 REST의 익명 점검은 401이므로 실제 일정 조회 성능 근거에서 제외한다. 내부 수치는 프로세스 실행·접속 비용을 포함하고 외부 수치는 인증 health HTTP이므로 직접적인 속도 비교나 이전 효과를 입증하지 않는다.

기존 이전 계획에는 최종 데이터 동기화·스키마/건수 대조와 Trip OAuth 설정 검증이 미완료로 기록돼 있다. 실제 전환 시 기존 후보의 최신성 확인, 새 데이터 스냅샷, 로그인·RLS·공유 기능 검증, 복구 경로 확보를 선행한다. 이번에는 데이터 이전·운영 연결 변경 없이 상태와 지연만 확인했다. 점검 스크립트는 워크스페이스의 `.server-setup/trip-performance-inspect.ps1`이며 비밀값과 사용자 데이터를 출력하지 않는다.

## 최초 점검 당시 상태

이번 실행 결과: lint·typecheck 통과, 단위/DB 테스트 399건 중 396건 통과·3건 실패, 생산 빌드 통과. 로그인 E2E는 실행하지 않았다. 빌드에서 Supabase SDK의 Node.js 20 이하 지원 종료 예정 경고가 발생했으므로 로컬·CI·배포 런타임 정렬도 후속 작업에 포함한다.

실패한 테스트는 `queries.test.ts`의 사용자 역할 조회(owner 기대값에 null 반환), 마감 RPC 기대값 불일치, `actions.item.test.ts`의 좌표 스냅샷 기대값 불일치다. RPC 불일치는 코드에서 확인됐다. 나머지 두 건은 환경 의존 사용자 조회와 검색 공급자 mock의 영향을 분리해야 하며 운영 장애로 단정하지 않는다.

여행 검색·분류, 일정 빠른 찾기, 일정 CRUD, 날짜 이동, 숙박 기간 표시, 국내외 지도·장소 검색, 항공 입력, 투표, 초대·권한 관리, 공유 링크, JSON 내보내기가 이미 있다. 기존 기능을 다시 만드는 대신 아래 병목과 빈틈을 보완한다.

지도 공급자별 동적 로딩, 요청 내 여행·사용자 조회 캐시, 날짜 포매터 캐시, 일부 DB 병렬 조회도 적용돼 있다. `vercel.json`은 `icn1`을 지정한다. 과거 문서의 `iad1` 기록만으로 현재 배포 리전이 미국이라고 판단하면 안 된다. 실제 운영 리전과 DB 리전은 별도 확인 대상이다.

운영 계정으로 로그인한 화면 측정과 운영 DB 실행계획은 이번 정적 점검에 포함하지 않았다. 아래의 성능 영향은 코드 구조에 근거한 병목 후보이며, 개선율이나 운영 응답시간으로 해석하지 않는다.

## 실행 순서와 측정 기준

1. 현재 테스트 실패를 분류하고 재현 가능한 기준선을 만든다. 기존 변경을 기능·보안·테스트별로 검토한다.
2. 투표 마감 일관성, 검색 timeout, 상세 화면 오류·로딩 분리를 처리한다.
3. 검색용 전체 일정 조회와 투표 집계를 줄이고 인증·DB 왕복을 측정한다.
4. 지도 갱신과 대량 일정 렌더링을 최적화하고 화면 구성을 개선한다.
5. 실제 로그인 E2E 및 권한·공유 회귀 검증 후 배포한다. 확장 기능은 이후 별도 작업으로 진행한다.

측정은 동일한 데이터로 국내·해외 여행 각각 30/150/500개 일정, 투표 없음/다수, owner/viewer를 비교한다. 로컬 생산 빌드와 운영 결과를 분리하고 최초/반복 방문, 네트워크 조건, 반복 횟수를 기록한다. 기본 비교는 조건별 10회 중앙값으로 시작하고 운영 p95는 충분한 표본이 쌓인 뒤 사용한다.

- 페이지: TTFB, 첫 일정 표시, 지도 준비 완료, 전송량, hydration 이후 긴 작업.
- 검색: 전체 시간, 인증·여행 판정·외부 API 시간, 취소·timeout 복구.
- 편집: 클릭 직후 피드백, 저장 완료, 재조회 수, 지도 위치 유지, 충돌 복구.
- DB: 요청 수, 응답 행·바이트, 실행계획, 권한별 결과.

성공 기준은 측정 전 목표값을 정하고 같은 조건에서 전후를 비교하는 것이다. 속도 향상과 함께 시간대·RLS·공유 비공개 정보·키보드 조작 회귀가 없어야 한다. 사용자별 여행 데이터를 전역 캐시에 넣는 방식으로 속도를 높이지 않는다.
