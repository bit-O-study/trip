# ADR-0001: 항공 데이터 공급자 선정

- 상태: **잠정 (어댑터 구현 완료 · 실측 검증 미완료)**
- 작성일: 2026-08-19
- 갱신일: 2026-09-04
- 결정 기한: 실제 API 키 발급 직후

---

## 배경

편명과 출발일로 실제 운항편을 조회해 일정에 저장해야 한다. 공급자는 `src/features/flights/provider.ts`의 공통 `FlightSearchResult` 타입 뒤에 adapter로 격리하므로, **공급자 선정이 늦어져도 다른 단계의 구현을 막지 않는다.**

## 후보

### A. 공공데이터포털 — 한국공항공사_실시간 항공기 운항정보 조회_GW

기존 `한국공항공사_항공기 운항정보` API는 **2026년 6월 12일 공지로 폐기**됐고 위 GW API로 전환됐다. 기존 서비스 URL은 **공지 후 90일만 유지**된다(2026년 9월 중 중단). 따라서 인터넷의 기존 예제·블로그는 대부분 폐기된 엔드포인트를 가리키므로 신뢰하지 않는다.

- 비용: 무료
- 활용 신청 승인에 1~2일 소요

### B. AeroDataBox

- 전 세계 편명 커버리지
- 판매 채널(RapidAPI / API.market / 직접)과 시점에 따라 **가격과 무료 단위가 다르다.** 발급 시점에 가격표를 직접 확인하고 아래 표에 기록한다.

### C. 기타 (AviationStack, FlightAware AeroAPI 등)

A·B가 요구사항을 못 채울 때만 검토한다.

## 잠정 결정 (2026-09-04)

**AeroDataBox를 1순위, 한국공항공사 GW를 2순위로 두고 어댑터를 먼저 구현했다.** 두 어댑터 모두 `src/features/flights/provider.ts`의 공통 타입 뒤에 있으므로, 실측 결과가 이 순서를 뒤집어도 고칠 곳은 어댑터와 `src/app/api/flights/search/route.ts`의 배열 하나다.

순서의 근거는 검증 항목 4번이다. 여행 계획은 수 주~수 개월 전에 세우는데, 한국공항공사 GW는 이름 그대로 **실시간** 운항정보라 그 시점의 조회에 답하지 못할 가능성이 높다. 답하지 못하는 공급자를 앞에 두면 대부분의 조회가 한 번씩 헛돈다.

> **이 결정은 실제 응답으로 확인한 것이 아니다.** 두 공급자 모두 발급된 키가 없어(`AERODATABOX_API_KEY`, `KAC_GW_API_KEY` 모두 비어 있음) 어댑터의 필드 매핑은 공개 문서의 스키마를 따랐을 뿐이다. 키를 넣고 첫 조회를 한 뒤 아래 표를 채우고, 매핑이 다르면 어댑터를 고쳐야 한다.

### 키가 없어도 막히지 않는다

공급자가 하나도 설정되지 않으면 검색은 `not_configured`로 실패하고, 화면은 **항상 노출되는 수동 입력 폼**으로 안내한다(architecture.md §1의 "항공편 검색 실패" 정책). 수동 입력 경로는 외부 API를 전혀 부르지 않으므로 지금 이 상태에서도 MVP 기준 3번의 "일정 저장"까지는 동작한다. 자동으로 채워 주는 부분만 빠져 있다.

### 확인한 것 / 확인하지 못한 것

| | 상태 |
|---|---|
| 편명 정규화 규칙 (`KE 0703` → `KE703`) | 단위 테스트로 확인 (`src/features/flights/provider.test.ts`) |
| 공급자 폴백 순서와 부분 실패 처리 | 단위 테스트로 확인 |
| 공항 코드 → IANA 시간대 매핑 | 주요 공항만 수록. 공급자가 시간대를 주면 그 값이 우선 |
| 위 12개 검증 항목 | **전부 미확인.** 키 발급 후 실측 필요 |
